# 领域文档

本文规定工程技能在探索和修改本仓库之前，应如何读取和使用领域文档。

## 探索代码前读取

开始探索与当前任务相关的代码前，按需读取：

- 仓库根目录的 `CONTEXT.md`。
- `docs/adr/` 中与准备修改区域有关的架构决策记录。

如果这些文件尚不存在，直接继续，不要将缺少文件本身视为问题，也不要为了补齐结构而预先创建空文档。

`CONTEXT.md` 和 ADR 由 `domain-modeling` 按需创建。通常会通过 `grill-with-docs` 或 `improve-codebase-architecture` 进入该流程，只有在确实澄清了领域术语或作出了需要长期保留的决策时才写入。

## 文档布局

本仓库采用单上下文布局：

```text
/
├── CONTEXT.md
├── docs/
│   └── adr/
└── app/
    └── src/
```

- `CONTEXT.md`：记录项目共享的领域术语、概念边界和明确避免使用的歧义表达。
- `docs/adr/`：记录难以撤销、会影响长期维护的架构决策。
- `docs/agents/`：记录工程技能自身的仓库级配置，不属于领域文档。

## 使用领域词汇

当输出内容命名领域概念时，包括 Issue 标题、重构建议、问题假设、测试名称和公共接口，应使用 `CONTEXT.md` 中已经定义的术语。

不要随意改用词义相近但边界不同的同义词。如果需要的概念尚未出现在词汇表中，应先判断：

1. 是否正在引入一个项目本身并不使用的新概念；如果是，应重新考虑。
2. 是否确实发现了领域词汇缺口；如果是，记录下来并交由 `domain-modeling` 澄清。

## 标明与 ADR 的冲突

如果拟议修改与现有 ADR 冲突，必须明确指出，不得静默覆盖已有决策。例如：

> 与 ADR-0007 中的既有决策冲突；考虑重新评估该决策，因为……

在新的决策被明确接受并记录之前，现有 ADR 仍然有效。
